# H30 — Consulta del promedio de calificaciones

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H30.

Frontend

1. La pantalla muestra pestañas “Por clase” y “Por entrenador”, tabla con nombre, promedio con un decimal y cantidad de evaluaciones; permite ordenar por promedio.
2. Una entidad sin evaluaciones muestra “Sin calificaciones”; no se representa como cero estrellas.
   Backend
3. El promedio por clase agrupa todas las sesiones COMPLETADA de la misma ClassTemplate; el promedio por entrenador agrupa evaluaciones de sesiones impartidas por ese entrenador.
4. Solo RECEPCION_ADMIN accede a estos reportes; MIEMBRO y ENTRENADOR reciben 403. Las evaluaciones inválidas no se cuentan y H39 usa la misma agregación por entrenador.

## Diseño backend e implementación

- **Módulo(s):** `reviews`.
- **Endpoint(s)/componente(s):** `GET /api/v1/reviews/averages?groupBy=class` o `GET /api/v1/reviews/averages?groupBy=trainer`; admite también `sort`, `page` y `pageSize`.
- **Modelos Prisma implicados:** `Review, ClassSession, ClassTemplate, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h30.seed.ts`; utiliza fixtures compartidos del grupo `core + classes` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/reviews/services/reviews.service.spec.ts`.

## Archivos fuente de referencia

- `src/reviews/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
