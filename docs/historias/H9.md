# H9 — Definición de horarios disponibles

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H9.

Frontend

1.  El entrenador crea un nuevo espacio eligiendo una fecha hasta 15 días después de la fecha actual y mediante una lista desplegable, selecciona una hora de inicio entre 06:00 AM y 08:00 PM; y la duración que será siempre de 60 minutos
2.  Al guardar se muestra «Espacio guardado» y el espacio aparece en «Mi disponibilidad», ordenado por fecha y hora ascendente, con estado LIBRE o RESERVADO. Los espacios LIBRE tienen las acciones Editar y Eliminar; los RESERVADO no las muestran.
3.  Al eliminar, el sistema pide confirmación con el texto «¿Eliminar este espacio?» y, tras aceptar, el espacio desaparece de la lista en la siguiente carga.
    Backend
4.  Rechaza con 409 «Ya tienes un espacio en ese horario» la creación o edición de un espacio con la misma fecha y hora de inicio que otro espacio del mismo entrenador, y con 400 «El horario debe ser posterior a la hora actual» un espacio con inicio en el pasado o a más de 15 días.
5.  Rechaza con 409 «El espacio tiene una sesión confirmada» la edición o eliminación de un espacio en estado RESERVADO.
6.  Solo un usuario ENTRENADOR crea, edita o elimina espacios, y únicamente los propios; un espacio de otro entrenador responde 404 y los demás roles reciben 403.

## Diseño backend e implementación

- **Módulo(s):** `trainer-slots`.
- **Endpoint(s)/componente(s):** `POST/GET/PATCH/DELETE /api/v1/trainer-slots`.
- **Modelos Prisma implicados:** `TrainerSlot, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h9.seed.ts`; utiliza fixtures compartidos del grupo `core + slots` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/trainer-slots/`.

## Archivos fuente de referencia

- `src/trainer-slots/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
