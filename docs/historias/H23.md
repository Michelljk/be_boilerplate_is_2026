# H23 — Consulta de rutina vigente e historial

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H23.

Frontend

1. La rutina VIGENTE muestra nombre, objetivo, entrenador, inicio, fin, versión y ejercicios agrupados por día de la semana, ordenados por posición con series y repeticiones.
2. Regla única de vigente: una versión es visible como VIGENTE si el estado es VIGENTE y la fecha de consulta se encuentra entre startsOn y endsOn inclusive. Una vez superada endsOn, el servidor pasa la versión a FINALIZADA al consultar o mediante proceso programado; si existe una nueva versión vigente, la anterior queda REEMPLAZADA. El historial lista versiones por número descendente.
3. Sin rutina para la fecha actual aparece «Aún no tienes una rutina vigente» y una sección separada Historial; si no tiene versiones, muestra «Aún no tienes una rutina asignada».
   Backend
4. Solo devuelve rutinas cuyo memberId corresponda al usuario autenticado; no acepta otro memberId de cliente para esta consulta.
5. No permite a otro miembro ver estas rutinas (404 cuando intenta acceder por ID) ni a un usuario sin rol miembro acceder al área (403).

## Diseño backend e implementación

- **Módulo(s):** `routine-queries`.
- **Endpoint(s)/componente(s):** `GET /api/v1/training-routines/me; GET /api/v1/training-routines/:id`.
- **Modelos Prisma implicados:** `TrainingRoutine, RoutineExercise, Exercise`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h23.seed.ts`; utiliza fixtures compartidos del grupo `core + routines` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `Pruebas de módulo y validación descritas en el catálogo del backend.`.

## Archivos fuente de referencia

- `src/routine-queries/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
