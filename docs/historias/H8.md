# H8 — Lista de reservas y registro de asistencia de una sesión

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H8.

Frontend

1. La pantalla muestra clase, fecha/hora, cupo máximo, número de reservas CONFIRMADA y tabla con nombre, número de miembro, estado de reserva y asistencia (PENDIENTE, ASISTIO, NO_ASISTIO); ordena por nombre del miembro ascendente y pagina de 10 en 10.
2. Antes de la hora de inicio, la asistencia es de solo lectura y se muestra «La asistencia se habilita al iniciar la sesión»; después del inicio el entrenador puede marcar cada reserva confirmada como Asistió o No asistió.
3. Si no hay reservas muestra «No hay miembros inscritos». Una reserva cancelada puede mostrarse separada como histórica, pero no cuenta en el total de asistentes ni admite marcar asistencia.
   Backend
4. Solo el entrenador asignado a esa sesión consulta la lista o registra asistencia; para sesiones de otro entrenador devuelve 403 o 404 sin divulgar inscritos.
5. Solo acepta attendance igual a ASISTIO o NO_ASISTIO desde el inicio de una sesión EN_CURSO, con reserva CONFIRMADA; antes del inicio, tras cancelación o para reserva cancelada devuelve 409.
6. Al finalizar el horario, el entrenador puede cerrar la lista: los PENDIENTE de reservas confirmadas pasan a NO_ASISTIO, la sesión cambia a COMPLETADA y se conserva fecha/autor. Una sesión completada ya no admite modificaciones normales y sirve para verificar H29/H39.

## Diseño backend e implementación

- **Módulo(s):** `class-attendance`.
- **Endpoint(s)/componente(s):** `GET /api/v1/class-sessions/:id/attendees; PATCH /api/v1/class-reservations/:id/attendance; PATCH /api/v1/class-sessions/:id/complete`.
- **Modelos Prisma implicados:** `ClassSession, ClassReservation, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h8.seed.ts`; utiliza fixtures compartidos del grupo `core + classes` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/class-attendance/services/class-attendance.service.spec.ts`.

## Archivos fuente de referencia

- `src/class-attendance/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
