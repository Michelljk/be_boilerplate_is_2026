# H18 — Historial de pagos del miembro

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H18.

Frontend

1. El miembro visualiza una lista con la fecha y hora del pago, concepto, monto en USD con dos decimales y estado, ordenada del pago más reciente al más antiguo.
2. El miembro puede filtrar su historial mediante un rango de fechas, utilizando los campos Desde y Hasta, y descargar el comprobante correspondiente mediante el botón «Descargar PDF».
3. Cuando no existen pagos para el período seleccionado, el sistema muestra el mensaje «No tienes pagos en este periodo».
4. Si la fecha final es anterior a la inicial, el sistema muestra «La fecha final no puede ser anterior a la inicial». Si el rango supera los 12 meses, muestra «El rango no puede superar 12 meses».
   Backend
5. El sistema devuelve únicamente los pagos del miembro autenticado con estado PAGADO o ANULADO, ordenados por fecha de pago descendente y paginados de 10 en 10. Los pagos PENDIENTE no aparecen en el historial.
6. El sistema incluye los pagos correspondientes a los conceptos MEMBRESIA, SESION_ADICIONAL y SESION_PERSONAL, utilizando el catálogo de conceptos definido en los supuestos compartidos.
7. El servidor rechaza con HTTP 400 los rangos donde la fecha final sea anterior a la inicial o que superen 12 meses, devolviendo el mensaje de error correspondiente.
8. El miembro no puede consultar pagos ni descargar comprobantes de otros usuarios. El servidor obtiene el memberId de la sesión autenticada y rechaza el acceso a recursos ajenos con HTTP 404.
9. El sistema permite descargar comprobantes mediante el servicio definido en H17. No se genera un segundo comprobante al consultar el historial.
10. Los usuarios con rol ENTRENADOR o RECEPCION_ADMIN no pueden acceder al historial personal de un miembro mediante este endpoint y reciben HTTP 403.

## Diseño backend e implementación

- **Módulo(s):** `payments`.
- **Endpoint(s)/componente(s):** `GET /api/v1/payments/history/me`.
- **Modelos Prisma implicados:** `Payment, Receipt`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h18.seed.ts`; utiliza fixtures compartidos del grupo `core` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `Pruebas de módulo y validación descritas en el catálogo del backend.`.

## Archivos fuente de referencia

- `src/payments/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
