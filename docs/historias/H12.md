# H12 — Consulta de agenda del entrenador

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H12.

Frontend

1. La agenda muestra por cada sesión fecha, hora, nombre y memberNumber del miembro y estado (CONFIRMADA, CANCELADA o COMPLETADA); ordena por fecha y hora ascendente y marca las CANCELADA con una etiqueta de ese nombre.
2. El entrenador alterna entre vista diaria (el día seleccionado) y semanal (de lunes a domingo de la semana que contiene el día seleccionado). Sin sesiones, se muestra «No tienes sesiones en este periodo».
3. En las sesiones CONFIRMADA cuyo inicio ya pasó aparecen los botones «Asistió» y «No asistió»; al elegir uno, el mensaje es «Asistencia registrada» y la sesión cambia a estado COMPLETADA.
   Backend
4. Solo registra asistencia en sesiones CONFIRMADA cuando la hora actual es posterior a startsAt; antes responde 409 «Solo puedes registrar asistencia después de la hora de inicio».
5. No permite registrar asistencia en una sesión CANCELADA ni modificar la asistencia de una sesión ya COMPLETADA (409 «La sesión ya tiene asistencia registrada»).
6. Un entrenador no puede ver ni modificar la agenda de otro entrenador: una sesión ajena responde 404 y los roles MIEMBRO y RECEPCION_ADMIN reciben 403.

## Diseño backend e implementación

- **Módulo(s):** `trainer-agenda`.
- **Endpoint(s)/componente(s):** `GET /api/v1/trainers/me/agenda; PATCH /api/v1/personal-sessions/:id/attendance`.
- **Modelos Prisma implicados:** `PersonalSession, TrainerSlot, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h12.seed.ts`; utiliza fixtures compartidos del grupo `core + slots` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/trainer-agenda/`.

## Archivos fuente de referencia

- `src/trainer-agenda/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
