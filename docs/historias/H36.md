# H36 — Reporte de ocupación de clases

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H36.

Frontend

1. Para el rango elegido, el reporte muestra por clase el cupo total del rango, las reservas confirmadas y el porcentaje de ocupación con un decimal.
2. El reporte ordena las clases de mayor a menor ocupación y resalta con la etiqueta «Alta» las 3 con mayor y con «Baja» las 3 con menor ocupación. Con menos de 6 clases, la mitad superior es Alta, la inferior es Baja y la clase central, si la hay, queda sin etiqueta.
3. Con igual porcentaje, queda primero la clase con más reservas confirmadas y después la de nombre alfabético menor.
   Backend
4. Por clase por semana se suman todas sus sesiones del rango.
5. El sistema no permite un rango mayor a 12 meses ni uno cuya fecha final sea anterior a la inicial (400), y no cuenta las reservas canceladas en la ocupación.
6. MIEMBRO y ENTRENADOR reciben 403 y el mensaje «Acceso denegado».

## Diseño backend e implementación

- **Módulo(s):** `reports`.
- **Endpoint(s)/componente(s):** `GET /api/v1/reports/occupancy`.
- **Modelos Prisma implicados:** `ClassTemplate, ClassSession, ClassReservation`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h36.seed.ts`; utiliza fixtures compartidos del grupo `core + classes + slots + routines + machines` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/reports/reports-math.spec.ts`.

## Archivos fuente de referencia

- `src/reports/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
