# H25 — Visualización de mi evolución física

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H25.

Frontend

1. Con dos o más registros presenta gráfica de líneas: eje X = fecha de medición ascendente; eje Y = peso corporal en kg. El miembro puede elegir una medida (cintura, pecho, brazo) para ver otra gráfica de líneas con eje Y en cm, sin unir puntos sin valor.
2. La vista muestra diferencia último valor − primer valor en kg y por cada medida con datos. También permite filtrar por ejercicio para ver gráfica de líneas de peso levantado (kg) por fecha (eje X); las repeticiones se muestran en etiqueta de cada punto, no se suman al peso.
3. Con menos de dos registros de peso muestra «Registra al menos 2 mediciones para ver tu evolución» y no presenta una gráfica vacía. Un filtro sin marcas muestra «No hay registros para este ejercicio».
   Backend
4. Los cálculos utilizan registros del miembro autenticado, ordenados por fecha; diferencia = valor del último registro disponible menos el primero con dato de ese indicador, sin inventar cero para medidas omitidas.
5. Ningún miembro accede a series ni métricas de otro (404); otros roles no entran en la ruta personal (403).

## Diseño backend e implementación

- **Módulo(s):** `progress`.
- **Endpoint(s)/componente(s):** `GET /api/v1/progress-records/me; GET /api/v1/progress-records/me/evolution`.
- **Modelos Prisma implicados:** `ProgressRecord, ExerciseMark`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h25.seed.ts`; utiliza fixtures compartidos del grupo `core + routines` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/progress/services/progress.service.spec.ts`.

## Archivos fuente de referencia

- `src/progress/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
