# H27 — Registro y actualización del estado de mantenimiento

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H27.

Frontend

1. Administración ve una tabla de máquinas con nombre, tipo, ubicación y estado; el botón “Registrar mantenimiento” abre un formulario con motivo y fecha de inicio.
2. Al cerrar un mantenimiento, el administrador introduce fecha de fin y la máquina vuelve a DISPONIBLE; se conserva el período en historial.
   Backend
3. No se permite abrir mantenimiento para una máquina inexistente, ni abrir dos mantenimientos simultáneos para la misma máquina.
4. EN_MANTENIMIENTO indica reparación programada o activa; FUERA_SERVICIO indica equipo inutilizable sin mantenimiento activo o pendiente de diagnóstico. Cada cambio registra autor y fechas.

## Diseño backend e implementación

- **Módulo(s):** `machine-administration`.
- **Endpoint(s)/componente(s):** `POST /api/v1/machines/:id/maintenance; PATCH /api/v1/machines/:id/maintenance/:maintenanceId/complete; PATCH /api/v1/machines/:id/status`.
- **Modelos Prisma implicados:** `Machine, MachineMaintenance, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h27.seed.ts`; utiliza fixtures compartidos del grupo `core + machines` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `Pruebas de módulo y validación descritas en el catálogo del backend.`.

## Archivos fuente de referencia

- `src/machine-administration/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
