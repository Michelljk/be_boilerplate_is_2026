# H5 — Reserva de cupo en sesión grupal

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H5.

Frontend

1. Al seleccionar Reservar, se muestra una confirmación con clase, fecha, hora y sala; al aceptar, el mensaje es «Reserva confirmada» y en la siguiente carga de Mis reservas aparece en estado CONFIRMADA. La confirmación en pantalla pertenece a H5; la notificación en bandeja corresponde a H33.
2. Mis reservas, ruta /mis-reservas, muestra columnas clase, fecha, horario, entrenador, sala, estado y acción disponible; ordena primero por fecha de inicio descendente, permite filtrar por estado (CONFIRMADA, CANCELADA, CANCELADA_POR_GIMNASIO), pagina de 10 en 10 y si no hay registros muestra «Aún no tienes reservas».
3. Si la membresía está vencida, no tiene clases restantes, la sesión ya empezó o no quedan plazas, la interfaz muestra el motivo devuelto por el servidor y no confirma la reserva.
   Backend
4. Solo admite sesiones PROGRAMADA, con startsAt > hora actual, membresía elegible, saldo suficiente si aplica y plazas disponibles. Rechaza un segundo intento de reserva de la misma sesión con 409 y mensaje «Ya tienes una reserva para esta sesión».
5. Rechaza solapamientos entre reservas CONFIRMADA del mismo miembro (inicioA < finB y finA > inicioB), así como sesiones llenas (409).
6. Dos solicitudes concurrentes por el último cupo producen exactamente una reserva confirmada; las validaciones, inserción y reducción de saldo (si corresponde) se realizan transaccionalmente con bloqueo/reintento controlado.
7. El miembro no puede consultar, reservar ni modificar reservas de otro miembro (404 para recursos ajenos).

## Diseño backend e implementación

- **Módulo(s):** `class-reservations`.
- **Endpoint(s)/componente(s):** `POST /api/v1/class-reservations; GET /api/v1/class-reservations/me`.
- **Modelos Prisma implicados:** `ClassSession, ClassReservation, Membership`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h5.seed.ts`; utiliza fixtures compartidos del grupo `core + classes` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/class-reservations/domain/reservation-rules.spec.ts`.

## Archivos fuente de referencia

- `src/class-reservations/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
