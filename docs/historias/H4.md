# H4 — Consulta de sesiones grupales disponibles de la semana

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H4.

Frontend

1. La vista muestra las sesiones con fecha, hora de inicio, duración en minutos, nombre de clase, entrenador, sala, cupo máximo y cupos libres; ordena primero por fecha/hora ascendente.
2. El rango visible inicia hoy y termina seis días después (siete días calendario locales). Se puede filtrar por nombre de clase (contiene texto, sin distinguir mayúsculas), sala y entrenador. Sin resultados, muestra «No hay sesiones disponibles para estos filtros».
3. Una sesión con cero cupos libres muestra «Llena» sin botón de reserva; una CANCELADA, COMPLETADA o ya iniciada no ofrece reserva.
   Backend
4. Los cupos libres se calculan como capacity - count(reservas CONFIRMADAS) para esa sesión; nunca son negativos.
5. No se devuelven sesiones canceladas por defecto ni sesiones sin fecha dentro del rango consultado; la consulta no expone datos personales de los inscritos.

## Diseño backend e implementación

- **Módulo(s):** `class-queries`.
- **Endpoint(s)/componente(s):** `GET /api/v1/class-sessions`.
- **Modelos Prisma implicados:** `ClassTemplate, ClassSession, Room, User`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h4.seed.ts`; utiliza fixtures compartidos del grupo `core + classes` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `src/class-queries/`.

## Archivos fuente de referencia

- `src/class-queries/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
