# H28 — Consulta de disponibilidad de máquinas

## Historia y criterios

Fuente: _HISTORIAS_USUARIO_GKDS_PROYECTO_2_IS_02_2026.pdf_, historia H28.

Frontend

1. Cada máquina aparece en una tarjeta con nombre, tipo, ubicación y estado; etiquetas y colores: verde DISPONIBLE, amarillo EN_MANTENIMIENTO, rojo FUERA_SERVICIO, acompañados siempre de texto.
2. Se puede filtrar por estado y ubicación; si no hay coincidencias, se muestra “No hay máquinas con esos filtros”.
   Backend
3. El endpoint devuelve la información vigente de las máquinas, sin exponer datos personales de responsables de mantenimiento.
4. Un MIEMBRO no puede ejecutar métodos para modificar estados de máquinas, aunque intente llamar el backend directamente.

## Diseño backend e implementación

- **Módulo(s):** `machine-queries`.
- **Endpoint(s)/componente(s):** `GET /api/v1/machines`.
- **Modelos Prisma implicados:** `Machine`. Se declaran en el esquema único `prisma/schema.prisma`; no se mantiene un schema independiente por historia.
- **Datos demo:** seed de historia `prisma/seeds/h28.seed.ts`; utiliza fixtures compartidos del grupo `core + machines` para conservar coherencia entre historias y permitir repetir el seed.
- **Pruebas asociadas:** `Pruebas de módulo y validación descritas en el catálogo del backend.`.

## Archivos fuente de referencia

- `src/machine-queries/`
- `prisma/schema.prisma`
- `prisma/migrations/` (historial SQL acumulativo; una migración puede cubrir varias historias).

> El seed prepara cuentas y datos base de demostración; no simula acciones transaccionales sensibles (p. ej. cobrar, cancelar, registrar asistencia) como si un usuario las hubiera ejecutado. Esas operaciones se prueban llamando a la API con la identidad y rol adecuados.
